## 三、最值得优先检查的技术问题

### 1. 储能 SOC 与能量平衡是否正确

假设充电功率 $P_c$、放电功率 $P_d$ 均为非负数，时间步长为 $\Delta t$，则常见的储能能量更新公式为：

$E_{t+1} = E_t + \eta_c P_{c,t}\Delta t - \frac{P_{d,t}\Delta t}{\eta_d}$

其中：



* $E_t$：时段初的储能电量，单位为 kWh。

* $P_c, P_d$：充放电功率，单位为 kW。

* $\eta_c, \eta_d$：充放电效率。

* $\Delta t$：时间步长，单位为小时。

如果使用 SOC 表示状态，还应满足：

$SOC_{\min} \le SOC_t \le SOC_{\max}$

以及设备额定充放电功率约束。

重点排查问题：



* 充电和放电的效率是否使用正确，是否在同一个时段重复计入。

* SOC 更新是否遗漏时间步长，或将 kW 与 kWh 混用。

* 是否允许同一时段同时充电和放电。

* 初始 SOC、最终 SOC 是否设置合理，是否存在通过耗尽初始储能虚增收益的问题。

* 是否考虑逆变器功率限制和储能容量限制。

### 2. IPSO 是否真正实现了有效优化

README 提到了改进粒子群算法，但仅有算法名称并不能证明其实现正确。



* **粒子编码与可行性**：检查粒子的位置是否对应实际可执行的充放电计划，速度和位置更新后是否超出物理约束。

* **目标函数方向**：如果目标是最大化收益，算法是否正确处理最大化与最小化；如果采用惩罚函数，惩罚系数是否足以避免不可行解。

* **收敛与稳定性**：多次运行不同随机种子，比较最优目标值、约束违反情况和收敛曲线，避免只展示一次偶然的好结果。

* **基线对比**：与不优化的规则策略、简单峰谷套利策略，以及小规模问题的精确优化解进行比较，判断 IPSO 是否真正带来收益。

> 尤其要注意：
>
> **算法返回了一个最优值，不等于它找到了满足所有约束的可行解。**
>
>  这两件事需要分别验证。

### 3. 电费、收益与零碳指标是否重复计算

源网荷储模型经常会同时统计购电成本、储能套利收益、光伏消纳收益和碳减排收益。如果没有统一的核算边界，可能出现重复计入。

建议统一定义每个时段的电力平衡：

$P_{\text{grid},t} + P_{\text{PV},t} + P_{d,t} = P_{\text{load},t} + P_{c,t} + P_{\text{export},t} + P_{\text{loss},t}$

具体形式需要根据模型是否显式计算损耗、是否允许售电等条件调整。

随后分别验证：



* 购电成本是否使用正确的分时电价。

* 储能充电是否产生相应的购电成本。

* 放电收益是否与减少购电成本重复统计。

* 光伏发电量、实际消纳量、弃光量是否满足一致的能量核算关系。

* 碳减排是否使用明确的电网排放因子，以及是否将储能转移的电量误当作新增清洁能源。

> 对于零碳园区，储能主要改变电力的时间分布，并不会自动创造新的可再生能源。若没有明确的碳核算边界，零碳指标可能失真。

### 1. 储能 SOC 与能量守恒必须先修

目前放电逻辑的核心问题是：



```
out = min(p\_batt\[t], soc\[t] \* C.STORAGE\_CAP\_MWH)

...

soc\[t + 1] = soc\[t] - from\_batt / C.STORAGE\_CAP\_MWH / C.ETA\_DISCHARGE
```

这里把电池当前的全部存储能量都视为可放电能量，忽略了最低 SOC 预留。更合理的放电上限应基于：

$E_{\text{dis,max}} = \max(0, SOC_t - SOC_{\min}) \, E_{\text{cap}} \, \eta_{\text{dis}}$

充电也应统一功率侧与电池内部能量的定义。如果 `ch` 是交流侧输入功率，那么在 1 小时时间步下，SOC 更新应反映充电效率：

$SOC_{t+1} = SOC_t + \frac{P_{\text{ch}} \, \Delta t \, \eta_{\text{ch}}}{E_{\text{cap}}}$

放电、充电都应先按剩余可用能量和额定功率裁剪实际功率，再更新 SOC，并在每一步校验上下限。还应区分请求功率与实际执行功率，后续指标必须使用实际功率计算。

### 2. 停电场景需要独立的孤岛功率平衡

目前普通场景的逻辑会将剩余负荷计入 `p_grid`；停电场景的目标函数却另行计算缺供电量。这会导致同一组仿真结果同时隐含 "电网能供电" 和 "电网不可用" 两种假设。

应急场景应明确设置电网不可用，令电网交换功率为零，并根据光伏实际出力、储能可用能量、储能功率上限和关键负荷计算供电缺口。若要评估 "关键负荷供电 4 小时以上"，还需要显式定义关键负荷曲线，而不是只用总负荷乘以一个场景系数。

### 3. 日内滚动调度要改成真正的局部时域优化

`ThreeLayerScheduler.intraday()` 将数据切成 4 小时片段，但 `ParkEnvironment.step()` 仍使用 `self.H = 24`。因此，优化器访问第 5 个时段时就会越界。

修复不能仅将 `self.H` 临时改成 4：滚动优化还必须把窗口起始 SOC 传递到下一窗口，保证各窗口之间能量状态连续；否则即使消除数组越界，也可能出现日内计划整体 SOC 不可行的问题。

### 4. 指标计算还有几个会误导决策的问题



* **碳排放少算 1000 倍**：`environment.py:172` 中，`p_grid` 按 MW 处理，每个时间步为 1 小时，累计得到的是 MWh；排放因子却使用 kg/kWh。计算时需要统一单位，按当前变量定义应换算为 kWh 后再乘排放因子。否则报告里的碳排放量级错误。

* **峰谷差削减率没有使用真实净负荷**：`environment.py:159–164` 使用请求的 `p_batt`，且未纳入光伏出力，也没有使用实际执行的储能功率。即使 SOC 已经不允许继续放电，指标仍可能认为储能在削峰。

* **充电成本可能被高估或错计**：`environment.py:148–152` 对全部充电量按电价计费，但模型也允许用光伏富余电量充电。应将电网充电量和光伏充电量分开计价，并明确采用的是增量收益还是园区整体购电成本。

* **需求响应补贴没有一致地进入优化目标**：`daily_revenue_breakdown()` 通过 `getattr(d, "dr_cut", [])` 读取信号，但 `d` 是字典，而且 `step()` 返回的 `detail` 并未保存这两个信号，因此该函数中的需求响应补贴计算会失效。另一方面，年收益函数又按全部峰段、谷段充电量估算补贴，不严格对应实际触发的响应时段。

* **场景缩放存在重复应用**：`scenes.py` 中光伏大发和低负荷场景已设置缩放值，`environment.py:34–44` 又对相应场景额外乘以 1.15 或 0.55。这会使部分场景偏离配置中声明的缩放比例；光伏出力还会被上限截断。

### 5. "IPSO 优于基线" 的对比目前还不够可靠

`run_simulation.py:80–92` 中，启发式基线通过 `base.run()` 自行生成一组随机场景数据；每次 IPSO 重启又调用 `env.state()` 生成新数据。因此，基线与优化策略，以及不同重启之间，可能面对的根本不是同一条负荷和光伏曲线。

这意味着即使报告显示 IPSO 的综合目标值更高，也不能据此证明算法优于基线。正确做法是：

> **每个场景只生成一次输入状态，并将同一个状态传给基线与所有优化重启。**
>
>  再分别报告目标函数、约束可行性和实际运行指标。

此外，优化器在搜索阶段使用了 SOC 和循环次数罚项，但最终返回的 F 是未经这些罚项修正的目标值；实时修正也不保证循环次数满足限制。因此，最终策略仍需进行一次独立的约束验收。

## 六、建议修复顺序

建议不要先调大粒子数、增加迭代次数或继续调整权重，而是按下面顺序处理：



1. **先修复物理模型**。统一充放电功率、SOC、效率和时间步长的定义；强制满足 SOC、额定功率和可用能量约束。

2. **修复场景与功率平衡**。停电时禁用电网供电；需求响应要真实改变负荷；避免场景缩放重复计算。

3. **修复滚动调度**。正确处理局部时间窗口、窗口间 SOC 传递和边界时段。

4. **修复经济与碳指标**。统一 MWh/kWh 单位，区分光伏充电与电网充电，按真实响应时段核算补贴。

5. **最后验证优化算法**。在相同输入下比较 IPSO 与基线，并检查每个输出策略是否满足约束；使用多个固定随机种子检验稳定性。

## 七、完整仓库新增发现

把完整仓库与优化版逐文件对照后，还发现几个之前仅看 Python 核心模块不容易发现的问题。

### 1. 前端参数导出与仿真入口基本接通，但缺少参数校验

两个 HTML 页面都会导出 `params.json`，优化版 `run_simulation.py` 也会读取该文件；常规参数名和 SOC、效率的百分比转换基本对应得上。

但后端 `apply_params()` 主要做类型转换，没有系统验证参数是否合理。例如：



* `soc_min >= soc_max` 或效率大于 1 时，没有明确拒绝。

* 储能容量、负工作天数等异常参数可能进入计算。

* 如果 `scenes` 非空，但其中全部是无效场景名称，过滤后会得到空列表，程序仍可能输出没有场景结果的报告。

* 权重没有校验是否非负、是否符合预期的归一化规则。

建议在 `apply_params()` 中增加统一校验；非法输入应明确报错，而不是静默生成看似成功的结果。

### 2. 两个场景的缩放被重复应用

`ems_sim/scenes.py:11–15、21–25` 已将光伏大发和应急备用场景的负荷缩放设为 0.55，但 `environment.py:42–44` 又对这两个场景额外乘以 0.55。

因此，按照当前调用链：



* 光伏大发场景负荷约为标准曲线的 $0.55^2 = 0.3025$，而不是预期的 55%。

* 应急备用场景也有相同的重复缩放。

* 光伏大发场景的光伏出力也重复乘以 1.15，之后再被上限截断。

这会改变优化器所面对的负荷与光伏比例，影响弃光量、收益、储能策略和应急保供结果。

### 3. 需求响应的 "削峰" 尚未真正作用于功率平衡

`environment.py:95–98` 计算了 `curtail`，但后续仍使用原始负荷 L 计算供电需求；`curtail` 只被保存到结果中，没有改变实际负荷或缺供电量。

与此同时，`daily_revenue_breakdown()` 读取的是字典中的需求响应字段，但仿真结果的 `detail` 并没有保存这些字段；代码还使用了 `getattr()` 读取字典属性，因此需求响应补贴计算无法按预期生效。

主报告中的年度收益函数则直接把峰段放电量、谷段充电量按补贴单价估算补贴，未验证实际响应事件、可申报电量和补贴资格。**这意味着当前模型的需求响应收益只能视为粗略假设，不能视为已验证的市场收益。**

### 4. 默认参数的实际运行结果不支持文档中的 "所有场景均优于基线"

已在完整压缩包中实际运行优化版主程序（4 个场景、每个场景 1 次优化重启），并检查了优化结果的 SOC 与指标。得到的结果如下：

## 八、进一步确认的核心缺陷

### P0：优化器的 SOC 罚函数方向写反了

文件：`ems_sim/optimizer.py:99–105`

当前代码：



```
pen\_soc = 8.0 \* (

&#x20;   max(0, (soc.min() - C.SOC\_MIN) \* cap) +

&#x20;   max(0, (C.SOC\_MAX - soc.max()) \* cap)

)
```

这两个方向都反了：



* SOC 低于下限时，第一项反而变成 0；SOC 高于上限时，第二项也变成 0。

* SOC 完全在合法范围内时，反而可能因为没有达到 SOC 上限而受到惩罚。

因此，优化器不仅没有正确惩罚 SOC 越限，还可能偏好不合理的策略。

**建议：** 将越限惩罚改为基于实际越限幅度的正向罚项，并纳入最终时刻的 `soc_end`。更重要的是，物理约束应当在每一步通过功率裁剪得到满足，不能只依赖罚函数。

### P0：碳排放指标少算 1000 倍

文件：`ems_sim/environment.py:172`



```
co2 = np.sum(np.maximum(p\_grid, 0) \* C.EMISSION\_GRID\_KG\_PER\_KWH)
```

`p_grid` 按 MW 表示，时间步为 1 小时，电网排放因子则按 kg/kWh 表示。计算前需要将 MWh 换算为 kWh。

按本次默认三次重启的结果，日常经济场景的优化后外购电量约为 61.55 MWh。按代码配置的排放因子估算，对应约 35,760 kg CO₂，而报告显示约 35.8 kg，量级相差 1000 倍。

这会直接影响碳排放报告及后续零碳达标论证。

### P1：目标函数没有统一量纲，权重难以实现预期效果

文件：`ems_sim/environment.py:145–170`

当前综合目标是经济收益、光伏消纳率和削峰指标的加权和，但三者尺度不同：



* 经济收益以元 / 日计，可能达到数千；

* 光伏消纳和削峰指标通常以 0–100 的数值计。

因此，即使经济权重只有 0.2，经济收益项仍可能显著压过权重为 0.65 的光伏消纳项。配置中的权重并不能直观反映各目标的真实影响力。

建议先统一各目标的量纲或归一化方式，再进行加权；同时报告各分项的原始值、归一化值及加权贡献，避免出现 "消纳权重最高，但优化主要在追求经济收益" 的情况。

### 第一步：重写储能 SOC 与功率平衡

这是整个项目最重要的修改。建议先修改 `ems_sim/environment.py` 的 `ParkEnvironment.step()`，不要直接在现有代码上不断追加 `if` 判断。

#### 1. 统一功率的正负号和单位

全项目统一定义：



| 变量                         | 统一定义       |
| -------------------------- | ---------- |
| `p_batt > 0`               | 储能向交流侧放电   |
| `p_batt < 0`               | 储能从交流侧充电   |
| `p_grid > 0`               | 从电网购电      |
| `pv`、`load`                | 单位均为 MW    |
| `dt`                       | 时间步长，单位 h  |
| `SOC`                      | 0～1 之间的比例  |
| `price`                    | 元 /kWh     |
| `EMISSION_GRID_KG_PER_KWH` | kg CO₂/kWh |

建议在 `config.py` 增加：



```
DT\_HOURS = 1.0
```

以后如果将模型扩展到 15 分钟级调度，只需要将时间步长设为 0.25，并同步修改时间序列和调度窗口，而不是把所有公式写死为 1 小时。

#### 2. 修正 SOC 的物理公式

电池额定容量为 $E_{\text{cap}}$，当前 SOC 为 $s_t$，最低和最高 SOC 分别为 $s_{\min}$、$s_{\max}$。

放电功率的交流侧上限应为：

$P_{\text{dis,max}} = \min\left( P_{\max},\; \frac{(s_t - s_{\min}) \, E_{\text{cap}} \, \eta_{\text{dis}}}{\Delta t} \right)$

充电功率上限应为：

$P_{\text{ch,max}} = \min\left( P_{\max},\; \frac{(s_{\max} - s_t) \, E_{\text{cap}}}{\eta_{\text{ch}} \, \Delta t} \right)$

对应的 SOC 更新公式为：

$s_{t+1} =
\begin{cases}
s_t - \dfrac{P_{\text{dis}} \, \Delta t}{E_{\text{cap}} \, \eta_{\text{dis}}}, & \text{放电} \\[6pt]
s_t + \dfrac{P_{\text{ch}} \, \Delta t \, \eta_{\text{ch}}}{E_{\text{cap}}}, & \text{充电}
\end{cases}$

这两个公式的前提是：`P_dis` 和 `P_ch` 都表示交流侧实际执行功率，而不是优化器请求的功率。

> **注意：**
>
>  不要只在 SOC 更新后使用 
>
> `np.clip()`
>
>  把越界值强行裁剪回去。那样会掩盖电量不守恒的问题。正确做法是先根据可用能量限制实际充放电功率，再更新 SOC，并断言结果在合法范围内。

#### 3. 重新组织 `step()` 的逐时计算逻辑

当前代码在充电分支里只将电网充电功率记入 `p_grid`，遗漏了光伏不能满足负荷时的购电功率。这意味着充电时段的电网购电量会被低估。

建议把每个时段拆成四步：



1. 计算实际需求响应后的负荷 `load_eff`。

2. 优先用光伏供负荷。

3. 按储能 SOC、额定功率和可用光伏余电决定实际充放电功率。

4. 计算电网购电、光伏弃电和 SOC 更新。

下面是可用于替换 `step()` 中核心逐时循环的示例。它假定 `p_batt` 是请求功率、正数代表放电、负数代表充电，并保留当前模型 "光伏优先供负荷" 的策略。



```
dt = C.DT\_HOURS

cap = C.STORAGE\_CAP\_MWH

pmax = C.STORAGE\_POWER\_MW

p\_actual = np.zeros(H)

p\_grid = np.zeros(H)

p\_pvuse = np.zeros(H)

p\_pvddiscard = np.zeros(H)

batt\_out\_hr = np.zeros(H)

batt\_in\_hr = np.zeros(H)

for t in range(H):

&#x20;   P = max(0.0, float(pv\[t]))

&#x20;   L = max(0.0, float(load\[t]))

&#x20;   # 1. 光伏优先满足负荷

&#x20;   pv\_to\_load = min(P, L)

&#x20;   residual\_load = L - pv\_to\_load

&#x20;   pv\_surplus = P - pv\_to\_load

&#x20;   req = float(np.clip(

&#x20;       p\_batt\[t], -pmax, pmax

&#x20;   ))

&#x20;   # 2. 实际执行功率：受功率和 SOC 双重限制

&#x20;   if req > 0:

&#x20;       available = max(

&#x20;           0.0, (soc\[t] - C.SOC\_MIN)

&#x20;           \* cap \* C.ETA\_DISCHARGE / dt

&#x20;       )

&#x20;       discharge = min(req, pmax, available, residual\_load)

&#x20;       soc\[t + 1] = (

&#x20;           soc\[t]

&#x20;           \- discharge \* dt

&#x20;           / (cap \* C.ETA\_DISCHARGE)

&#x20;       )

&#x20;       p\_actual\[t] = discharge

&#x20;       batt\_out\_hr\[t] = discharge \* dt

&#x20;       p\_grid\[t] = residual\_load - discharge

&#x20;       p\_pvuse\[t] = pv\_to\_load

&#x20;       p\_pvddiscard\[t] = pv\_surplus

&#x20;   elif req < 0:

&#x20;       charge\_request = -req

&#x20;       room = max(

&#x20;           0.0, (C.SOC\_MAX - soc\[t])

&#x20;           \* cap / (C.ETA\_CHARGE \* dt)

&#x20;       )

&#x20;       charge = min(charge\_request, pmax, room)

&#x20;       # 3. 光伏余电优先充电，剩余部分才从电网充电

&#x20;       pv\_charge = min(charge, pv\_surplus)

&#x20;       grid\_charge = charge - pv\_charge

&#x20;       soc\[t + 1] = (

&#x20;           soc\[t]

&#x20;           \+ charge \* dt \* C.ETA\_CHARGE / cap

&#x20;       )

&#x20;       p\_actual\[t] = -charge

&#x20;       batt\_in\_hr\[t] = charge \* dt

&#x20;       p\_grid\[t] = residual\_load + grid\_charge

&#x20;       p\_pvuse\[t] = pv\_to\_load + pv\_charge

&#x20;       p\_pvddiscard\[t] = pv\_surplus - pv\_charge

&#x20;   else:

&#x20;       soc\[t + 1] = soc\[t]

&#x20;       p\_actual\[t] = 0.0

&#x20;       p\_grid\[t] = residual\_load

&#x20;       p\_pvuse\[t] = pv\_to\_load

&#x20;       p\_pvddiscard\[t] = pv\_surplus
```

这段示例还需要你在外层补齐两个约束：



* **停电模式：** 不能简单地继续使用上面的 `p_grid` 计算。必须令电网交换功率为零，并明确处理负荷缺供、储能实际输出和光伏弃电。

* **需求响应模式：** 先计算有效负荷 `load_eff`，再使用它参与功率平衡；不能只计算 `curtail` 并保存，却不改变实际负荷。

另外，后续的 `res` 应返回 `p_actual`，而不是直接返回原始请求 `p_batt`。SOC、购电量、削峰率、循环次数和收益，都必须基于实际执行功率计算。

### 第二步：修复优化器的 SOC 罚函数

文件：`ems_sim/optimizer.py`，`_evaluate_pso()` 方法。

当前 SOC 罚函数的方向有误。可以先将它改成下面这种形式：



```
soc = r\["detail"]\["soc"]

soc\_all = np.append(soc, r\["detail"]\["soc\_end"])

low\_violation = np.maximum(

&#x20;   C.SOC\_MIN - soc\_all, 0.0

)

high\_violation = np.maximum(

&#x20;   soc\_all - C.SOC\_MAX, 0.0

)

pen\_soc = 10000.0 \* np.sum(

&#x20;   low\_violation \*\* 2 + high\_violation \*\* 2

)

pen\_cycle = 1500.0 \* max(

&#x20;   0.0, r\["cycles\_day"] - C.MAX\_CYCLES\_DAY

)

fitness = r\["F"] - pen\_soc - pen\_cycle

return fitness, r
```

这里的 `10000.0` 只是初始调试值，不是已经校准好的最优罚系数。应根据目标函数的量级、SOC 越限幅度和可行性测试调整。

> 但要特别注意：
>
> **罚函数只能帮助优化器选择可行策略，不能代替&#x20;**
>
> `step()`
>
> **&#x20;中的物理约束。**
>
>  即使优化器完全没有收敛，环境也必须保证实际 SOC 不越界。

#### 最终策略必须再验收一次

在 `optimize()` 返回策略前，建议增加一个独立的验收函数，至少检查：



* `SOC_MIN <= soc[t] <= SOC_MAX`，包括最后一个时刻的 SOC；

* `abs(p_actual[t]) <= STORAGE_POWER_MW`；

* `cycles_day <= MAX_CYCLES_DAY`；

* 电网功率是否满足场景约束；

* 充放电功率、购电量、弃光量和负荷缺供是否满足功率平衡。

如果策略不满足硬约束，应重新修复或重新优化，而不是只把违规策略的目标值打印到报告里。

### 第三步：重写经济性和碳排放计算

这部分建议在物理模型修好后再改，否则当前的购电量、充放电量本身就不可靠。

#### 1. 先修正碳排放单位

当前 `environment.py` 中：



```
co2 = np.sum(

&#x20;   np.maximum(p\_grid, 0)

&#x20;   \* C.EMISSION\_GRID\_KG\_PER\_KWH

)
```

`p_grid` 的单位是 MW，时间步为小时，排放因子是 kg/kWh，因此正确的购电碳排放计算应为：



```
dt = C.DT\_HOURS

grid\_import\_kwh = (

&#x20;   np.maximum(p\_grid, 0).sum()

&#x20;   \* dt \* 1000.0

)

co2\_kg = (

&#x20;   grid\_import\_kwh

&#x20;   \* C.EMISSION\_GRID\_KG\_PER\_KWH

)
```

同时要明确：如果 `p_grid` 只记录净购电量，那么电池充电导致的额外购电也必须被记录在内。否则碳排放仍然会少算。

#### 2. 经济收益不要把同一份电量重复算两次

当前代码计算了 `cost_grid_out`，但没有将其用于 `f_econ`。另一方面，又单独计算储能放电收益和充电成本。这种写法很容易把 "减少购电成本" 和 "放电收益" 重复计算。

建议把经济收益统一定义为：

$B_{\text{storage}} = C_{\text{grid,baseline}} - C_{\text{grid,actual}} - C_{\text{O\&M}} + R_{\text{valid subsidy}}$

其中：



* $C_{\text{grid,baseline}}$：不使用储能时的购电成本；

* $C_{\text{grid,actual}}$：采用当前策略后的实际购电成本；

* $C_{\text{O\&M}}$：储能运维成本；

* $R_{\text{valid subsidy}}$：符合场景和规则的实际需求响应补贴。

代码结构可以改为：



```
grid\_cost = np.sum(

&#x20;   np.maximum(p\_grid, 0)

&#x20;   \* C.DT\_HOURS

&#x20;   \* 1000.0

&#x20;   \* price

)

baseline\_grid\_cost = np.sum(

&#x20;   np.maximum(load - pv, 0)

&#x20;   \* C.DT\_HOURS

&#x20;   \* 1000.0

&#x20;   \* price

)

opex = (

&#x20;   batt\_in\_mwh + batt\_out\_mwh

) \* C.OPEX\_YUAN\_PER\_KWH

f\_econ = (

&#x20;   baseline\_grid\_cost

&#x20;   \- grid\_cost

&#x20;   \- opex

&#x20;   \+ valid\_dr\_revenue

)
```

这只是经济核算的结构示例。你还需要明确是否允许光伏上网、上网电价是多少、运维费是按充放电吞吐量还是按固定容量计算，以及是否有需量电费等项目。

> **尤其要注意：**
>
>  上面的 
>
> `baseline_grid_cost`
>
>  只有在基线与当前策略使用相同的负荷、光伏、时间步和电价时才可比较。若存在光伏弃电、上网和不同的充电来源，基线也要采用一致的能源分配规则。

#### 3. 需求响应补贴必须依据实际响应量

当前 `daily_revenue_breakdown()` 中用 `getattr(d, "dr_cut", [])` 读取字典字段，这是错误的读取方式；而且 `detail` 没有保存完整的需求响应时段。

建议：



* 在 `state` 中只生成一次 `dr_cut` 和 `dr_fill`；

* 将两个字段保存到仿真结果 `detail`；

* 通过 `d.get("dr_cut", [])` 读取；

* 使用实际执行的响应功率和响应时长计算补贴；

* 对应急备用、日常经济等不具备响应资格的场景，不计入补贴。

不要直接把所有峰段放电量都算作需求响应补贴。放电发生在峰段，不代表它一定是可申报的需求响应事件。

### 第四步：让基线和 IPSO 使用相同输入

文件：`run_simulation.py` 的 `run_scene()`。

当前代码先执行：



```
r\_base = base.run()
```

之后每次优化又执行：



```
o = opt.optimize(state=env.state())
```

这意味着基线和优化器可能使用不同的随机负荷、光伏曲线，比较结果不公平。

建议改成：



```
state = env.state()

r\_base = base.run(

&#x20;   state=state,

&#x20;   soc0=soc0

)

best = None

for rs in range(restarts):

&#x20;   opt = OPT.IPSOOptimizer(

&#x20;       env,

&#x20;       n\_particles=50,

&#x20;       n\_iter=120,

&#x20;       seed=7 + rs \* 11

&#x20;   )

&#x20;   opt.soc0 = soc0

&#x20;   o = opt.optimize(state=state)

&#x20;   # 这里应该优先比较可行解，再比较 fitness

&#x20;   if best is None or o\["fitness"] > best\["fitness"]:

&#x20;       best = o

r\_opt = best\["res"]
```

这里假设你在 `optimizer.py` 中把返回结构统一为包含 `fitness` 的字段，例如：



```
return {

&#x20;   "x": out,

&#x20;   "F": r\["F"],

&#x20;   "fitness": final\_fitness,

&#x20;   "res": r,

&#x20;   "history": history,

}
```

这样，所有优化重启面对相同输入，基线与优化器也面对相同输入。对比实验才有意义。

另外，`apply_params()` 也建议增加参数校验，至少拒绝以下情况：



* 容量或额定功率小于等于零；

* `SOC_MIN >= SOC_MAX`；

* 效率不在 $(0, 1]$ 范围；

* 负工作天数或负补贴；

* 场景过滤后为空列表；

* 权重为负、包含缺失项或全为零。

对于这些情况，应明确报错，不要静默使用错误配置继续计算。

### 第五步：修复场景缩放和日内滚动调度

#### 1. 取消重复场景缩放

文件：`ems_sim/scenes.py` 和 `ems_sim/environment.py`。

目前 `scenes.py` 已设置：



* `pv_absorb`：负荷缩放 0.55、光伏缩放 1.15；

* `blackout`：负荷缩放 0.55。

但 `environment.py` 又对部分场景重复缩放。**建议统一由&#x20;**`scenes.py`**&#x20;或调用入口负责场景参数，环境类只执行传入的缩放比例。**

因此，建议删除 `gen_pv()` 中针对 `pv_absorb` 的额外 `* 1.15`，并删除 `gen_load()` 中针对 `pv_absorb`、`blackout` 的额外 `* 0.55`。场景缩放只执行一次。

#### 2. 修复日内滚动调度

文件：`ems_sim/optimizer.py` 的 `ThreeLayerScheduler.intraday()`。

目前前 4 小时切片传入优化器，但环境仍然按照 24 小时运行，所以会产生数组越界。不要只把 `self.env.H` 改成 4，因为那样可能影响完整日曲线和其他模块。

更稳妥的做法是：



1. 创建一个支持可变时域长度的仿真环境，或让 `step()` 根据输入数组长度确定本次时域。

2. 每次滚动窗口都传入窗口起始 SOC。

3. 当前窗口结束 SOC 作为下一窗口的初始 SOC。

4. 重新计算每个窗口的可行策略，并把窗口结果拼接成完整 24 小时策略。

5. 最后在完整 24 小时输入上重新仿真，检查全日 SOC、循环次数和功率平衡。

滚动窗口的状态传递应该是：

$SOC_{\text{start},k+1} = SOC_{\text{end},k}$

如果每个窗口都从 20% SOC 开始优化，拼接后的整日策略就可能出现前后不连续的能量状态。

### 第六步：增加自动化测试

建议在正式修改前，新增 `tests/test_environment.py` 和 `tests/test_optimizer.py`。至少覆盖以下回归测试：



| 回归测试项       | 检查内容                                   |
| ----------- | -------------------------------------- |
| **SOC 不越界** | 任何时段 SOC 都在配置的最小值和最大值之间，包括日末 SOC。      |
| **充放电功率受限** | 实际执行功率不超过额定功率，SOC 接近边界时自动削减请求功率。       |
| **功率平衡**    | 光伏、负荷、储能、电网购电、弃光和缺供电量逐时对账。             |
| **停电时不购电**  | 孤岛场景的电网交换功率为零，缺供电量被正确统计。               |
| **碳排放单位**   | 1 MWh 外购电对应排放因子乘以 1000 kWh，而非直接乘以 MWh。 |
| **滚动窗口**    | 4 小时、6 小时和 24 小时窗口都能运行，窗口间 SOC 连续。     |
| **基线公平对比**  | 基线与 IPSO 使用相同负荷、光伏、电价和需求响应信号。          |
| **异常参数**    | 非法容量、效率、SOC 范围和空场景配置应被拒绝。              |

如果使用 pytest，测试命令可以是：



```
python -m pytest -q
```

在测试全部通过之前，不建议把仿真结果作为最终报告。

1. **先备份项目，单独建立修复分支。** 不要直接覆盖当前比赛版本，保留原始结果用于比较。
